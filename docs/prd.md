# AI Trip Pilot 产品文档（PRD）

> 状态：设计定稿，待实施 ｜ 版本 v0.1
> 术语一律以 [CONTEXT.md](../CONTEXT.md) 为准；实现细节见 [architecture.md](./architecture.md)；关键决策见 [docs/adr/](./adr/)。
> 一句话定位（业务对象在前）：**面向多约束行程的规划 Agent——约束求解 + 检索增强 + 回归评测**

---

## 1. 定位与成功标准

**产品定位**：一个窄而深、可验证的出行规划 Agent。**验收标准**：用真实数据跑通一条窄路径。

这两句话的含义是——当「技术展示密度」与「产品完整度」冲突时，选技术展示密度；但被保留下来的那条路径必须真实可跑，不能是 mock。

**成功标准（可判定，每个阶段逐条自检）**：

| # | 标准 | 判定方式 |
|---|---|---|
| C1 | 三条主线可现场演示 | 长途、短途、修改各跑一次，不依赖预录 |
| C2 | 回归集上红线违反数 = 0 | 评测脚本输出，进 CI |
| C3 | 至少 3 组消融数字 | 有/无求解器、单/双 Agent、有/无 RAG |
| C4 | 每个数字带口径 | 样本量、指标定义、基线、测量日期 |
| C5 | 一条完整的 badcase 迭代链 | 漏检 → Trace 定位 → 加断言 → 版本对比 → CI 阻断 |
| C6 | 三分钟录屏 + 可一键本地复现 | `docker compose up` 可跑通 |

> **编号说明**：这里用 **C1–C6** 表示**成功标准**（Criteria），与 §11 路线图的 **S1–S8** 分开——两者是不同维度：本题答的是「最终要满足什么」，路线图答的是「按什么顺序做」。初版两处都用 S 编号，会让人把「S1 阶段完成了」误读成「C1 已达成」——**S1 完成时，C1 一条都还没满足**。

**反向成功标准（明确不追求，写下来是为了拒绝诱惑）**：不追求覆盖全品类出行；不做通用旅行助手；不做真实预订；不追求「用户量」。

## 2. 问题与证据

**行业级证据（唯一被引用的一手学术结论）**：ACL 2025 Findings 的 [TripTailor](https://aclanthology.org/2025.findings-acl.503/) 基准（50 万+ 真实 POI、近 4,000 条真实行程）显示，**最新 SOTA 大模型生成的行程，达到人类水平的不到 10%**，失败集中在**可行性、合理性、个性化**。→ 结论：行程生成的主要矛盾不是「写得不够好听」，而是**方案在物理与时间上根本不成立**。

**来自公开项目扫描的通病**：把行程当景点清单（不校验营业时间、通勤耗时、地理聚集度）；单轮 prompt 出全文冒充 Agent（没有工具循环与失败重试）；数据接入浅（无票务/价格/天气校验）；POI 幻觉普遍。

**本项目不做「又一个模板」**：公开仓库里已有成熟的同类多 Agent 旅行规划模板，也有 OSM + Wikivoyage + 行程校验的中文实现。差异化只能来自三处——**约束求解**、**评测闭环**、**诚实的边界声明**。

**一条被我们主动拒绝引用的证据**：网上流传「纯 Prompt 方案硬约束满足率仅 63.7%，OR-Tools 可做到 100%」。该数字出自单篇自述博客，n=1、自报、无口径，因此**不作为论据写入任何文档**。我们采纳的只是它背后的机制论证（语言模型无法强制过滤约束），数字一律由本项目自己测出。这条纪律本身就是工程可信度的一部分。

## 3. 用户与使用方式

- **出行者**：作者本人 + 少数朋友。**不做注册登录**；架构上按会话隔离，为将来多用户预留。
- **使用方式**：本地一键启动的 Web 应用（对话区 + 方案卡片 + 右侧执行侧栏），另附 CLI 入口供评测与调试。
- **公开程度**：公开代码仓库；**不公网部署**（理由见 §9 合规）。演示靠录屏 + 可复现的本地环境。

## 4. 范围

### 4.1 三条主线

| 主线 | 典型输入 | 核心难点 | 技术落点 |
|---|---|---|---|
| **长途行程** | 「7 月去上海玩 5 天，从杭州出发，两个人，预算 6000」 | 跨城交通 + 住宿区域 + 每日容量三者联立 | 候选池构建、约束求解、硬约束校验 |
| **短途行程** | 「周六下午有空，想在我家附近逛逛，别太远」 | 时间窗口 + 停靠点排序 + 通勤时长 | 同城候选、顺序优化、返程时间 |
| **修改** | 「第二天换成室内的」「预算砍到 4000」 | 只重算受影响的部分，保留已确认内容 | 影响面判定、方案版本、断点续算 |

**为什么「修改」是一等公民而不是附属功能**：它是**方案版本**、**长期记忆**、**多轮意图识别**、以及「为什么不做全量重生成（成本与稳定性）」这一整套论证的唯一落点。没有它，编排图就退化成一条直线。

### 4.2 明确不做（no-s）

不做境外与签证；不做支付、预订、抢票、下单；不做酒店实时比价；不做多用户协作与分享；不做微信/小程序/App；不做通用旅行闲聊助手；不做微调与本地大模型部署。

### 4.3 本期砍单（成本收益判断）

按「太难或性价比低的不做」原则，以下功能**设计上砍掉**，并给出替代：

| 砍掉 | 替代方案 | 判断依据 |
|---|---|---|
| 三个方案变体 × 多 Agent 并行生成 | **同一次求解跑两档参数**（经济档/舒适档）+ 并行解说 | 保留「多方案」与 fan-out 展示，复杂度近乎为零；三 Agent 并行会让评测工作量 ×3 |
| 多人偏好冲突协商（多 Agent 谈判） | 同行人作为**约束字段**（带儿童→步行上限、室内优先、午休窗口） | 同行人约束**可校验**；偏好冲突协商**不可校验**，无法证明有效性 |
| 本地路网引擎（OSRM/Valhalla + 中国 OSM） | 真实路径用地图工具的路线规划（配额充足）；离线兜底用球面距离 × 经验系数并标注「估算」 | 下载与运维成本高，对本项目的技术叙事无增量 |
| 自托管可观测性平台（需额外三套中间件） | 托管版观测服务（免费层） | 「自建可观测性」的加分被运维踩坑时间抵消 |
| 公网部署 demo | 本地一键启动 + 三分钟录屏 | 合规成本（备案核查、配额用途）会吃掉整个演示阶段（S8） |
| 通用旅行问答、攻略社区、行程分享 | —— | 与定位冲突，稀释技术密度 |

**明确不砍**（这五项是项目的全部价值）：约束求解与确定性校验、双数据访问层、评测闭环与消融、修改主线、检索增强的双通道。

## 5. 产品红线

红线是**不可协商**的产品约束，每条都有对应的验收断言。

| 编号 | 红线 | 为什么 |
|---|---|---|
| R1 | **事实通道与知识通道互不混存**：结构化事实只走工具调用，非结构化文本只走检索 | 混存会让「事实」失去可追溯性，也是多数幻觉的来源 |
| R2 | **方案中每个停靠点都必须来自候选池**；语言模型不得生成任何候选池外的地名 | 把「不要幻觉」从 prompt 祈祷变成架构约束 |
| R3 | 不展示酒店实时价格；不出现「可预订 / 已预订」字样 | 个人开发者无合规的 OTA 数据渠道 |
| R4 | 票务数据必须显著标注「非官方、可能延迟、不保证准确」 | 数据源本身不可靠，标注是诚实义务 |
| R5 | 绝不提供抢票、下单、代购 | 法律与平台条款双重风险 |
| R6 | 不采集、不存储手机号、身份证、位置轨迹 | 个人信息保护法的最小必要原则 |
| R7 | 离线数据集内容必须标注为「示例数据」并带时间戳 | 不得把历史快照伪装成实时数据 |
| R8 | 约束不可行时必须澄清，不得静默放宽约束 | 「悄悄降低标准」是这类产品最隐蔽的失信 |

## 6. 功能规格

### 6.1 长途行程

- **输入**：自然语言；槽位包括出发城市、目的城市、日期或天数、同行人、预算上限、偏好。
- **流程**：抽取槽位 → 信息不全则澄清 → 构建候选池（跨城交通 / 住宿区域 / 每日地点）→ 求解硬约束 → 校验 → 成文与解说 → 交付方案。
- **不可行分支**：求解返回冲突的约束集合，Agent 用自然语言反问，例如「预算上限与这三个地点的门票、以及 5 天里 3 个郊区景点不能同时满足——放宽预算、减少一个郊区景点，还是把行程缩短一天？」
- **验收**：`demo/long-trip/*.json` 全部通过 §7 的红线断言。

### 6.2 短途行程

- **输入**：起点（常驻位置或显式指定）、可用时间窗口（如「周六 13:00–20:00」）、同行人、偏好。
- **流程**：同城候选构建 → 时间窗与通勤约束求解 → 排序 → 校验 → 交付。
- **验收**：同长途。

### 6.3 修改

- **输入**：针对某一份已确认方案的变更要求（换类型、砍预算、加同行人、改天数）。
- **流程**：载入目标方案版本 → 判定影响面 → 标记保留项 → 仅对影响面重算（候选补取 / 重排 / 重解 / 重校验）→ 生成新版本。
- **展示**：界面必须**逐条显示「保留了什么、重算了什么、为什么」**。这个展示本身就是「局部重规划」这一技术主张的证据。
- **验收**：①未受影响的部分逐字节不变（版本 diff 可证）；②影响面之外不产生新的工具调用；③新版本通过全部红线断言。

### 6.4 澄清

- **触发**：槽位缺失；约束不可行；需求自相矛盾。
- **要求**：
  - 一次只问一个批次的问题，不逐个追问。
  - **每个问题都必须让用户能一句话答完。** 这是唯一的硬要求。
  - **可枚举的槽位给选项**（预算档位、天数、同行人类型）——选项能大幅降低用户的输入成本。
  - **不可枚举的槽位给默认值而不是选项**（出发城市这类取决于用户自身的信息给不出有意义的选项，但可以预填「上次用的 / 常住城市」）。
  - 澄清轮数计入评测指标。

> 早期版本这条写的是「问题必须附带两个以上可执行选项」。那个要求过强：
> 对城市名这类槽位根本无法满足，最后只会被绕过。规则应当约束**用户能不能
> 轻松回答**，而不是约束形式。

> **S1 记账：本条有两项尚未实现，且都不是遗漏。**
>
> - **「可枚举的槽位给选项」现在无处生效**：可枚举的槽位（预算、天数、同行人）目前全是
>   **可选**槽位，而流程只会问**必需**槽位（出发城市、目的城市）——没有可问的枚举槽位，
>   选项就没有落点。
> - **「不可枚举的槽位给默认值」依赖尚不存在的东西**：预填「上次用的 / 常住城市」需要
>   **出行者画像**，那是 S5 的产出。
> - **「澄清轮数计入评测指标」同理**：计数器要等评测（S7）才有消费者。现在加进状态就是
>   一个没人读的字段——正是 [CONTRIBUTING.md](../CONTRIBUTING.md) 警告过的「声明了但没人用」。
>
> 三项都等各自的前置条件到位再补，届时一并改这条规则。

### 6.5 两档方案

在预算与节奏约束上跑两档参数（经济档 / 舒适档），并行生成解说，界面左右对比。这是「多方案」与并行编排的最低成本实现。

## 7. 评测方案

这是本项目的**主要证据来源**，不是附属工作。

### 7.1 红线断言（确定性，不依赖模型裁判）

| # | 断言 |
|---|---|
| A1 | 零虚构地名：方案中每个停靠点都能在候选池中按 ID 命中 |
| A2 | 时间无重叠（含移动段） |
| A3 | 所有停靠点在营业时间内 |
| A4 | 单日移动总时长与总停留时长不超阈值 |
| A5 | 总花费不超预算上限 |
| A6 | 返程可达（最后一日为返程预留足够时间） |
| A7 | 结构化输出符合 schema |
| A8 | 每条事实带来源标记 |

### 7.2 用例集

- **回归集（公开、进 CI）**：24 条 —— 长途 8、短途 8、修改 8；覆盖信息不全、预算极紧、天气突变、同行人约束冲突等边界。
- **隐藏挑战集（不进仓库）**：12 条 —— 防止针对公开用例过拟合。
- **外部可比基线（待定）**：若 TripTailor 数据集确实可得，用它做外部口径的可比评测，报「在公认基准的可行性维度上的表现」。**在数据集可得性核实完成前，这一条不写进结论。**

### 7.3 消融矩阵（回答「多这套东西到底有没有用」）

| 组 | 对照 | 观测 |
|---|---|---|
| A | 语言模型直出 + 事后校验 **vs** 求解器在环 | 红线违反数、澄清轮数、成本、P95 延迟 |
| B | 单 Agent **vs** 双 Agent（候选筛选 + 解说） | 软偏好满足度、成本、延迟 |
| C | 无检索 **vs** 有检索 | 解说质量（人工抽样校准）、个性化得分 |
| D（可选） | 免费模型 **vs** 付费模型 | 同口径对比 |

**诚实条款**：若消融显示双 Agent 相比单 Agent 没有可观收益，文档中的结论就是「本项目证据显示收益有限」，而不是硬凑多 Agent 的价值——这个诚实的结论比硬撑出来的价值更可信。

### 7.4 汇报纪律

每个数字必须同时给出：**样本量、指标定义、基线、测量日期**。没测过的写「未测」，不写估计值。禁止把框架能力写成自研。

## 8. 指标口径

| 指标 | 定义 | 目标 |
|---|---|---|
| 红线违反数 | §7.1 八条断言的失败总条数 | **0** |
| 可行性 | 方案满足全部硬约束（二元） | 全部为真 |
| 澄清轮数 | 一次规划中 Agent 反问的轮数 | 观察值，不设目标（越低越好但以正确为先） |
| 预算偏差 | 方案总花费与用户上限之差 | ≤ 0 |
| 单次成本 | 该次规划的全部模型与工具调用费用 | 记录并优化 |
| P95 延迟 | 首次响应与完整方案产出 | 记录并优化 |

**禁止使用的指标**：任何形如「准确率 95%」而不说明口径的说法；「可行性 80%」这种把二元性质当连续量的说法。

## 9. 数据源与合规

### 9.1 双路径

| 路径 | 用途 | 数据源 |
|---|---|---|
| **真实路径** | 演示、真实规划 | 地图服务官方 MCP（地点检索、路线、地理编码、天气）；社区只读票务接口（标注非官方） |
| **离线路径** | 开发、回归评测、CI、断网演示 | 许可明确的开源数据集落本地（POI + 行程），球面距离估算，免费天气接口 |

两条路径共用同一组数据访问接口，靠环境变量切换（详见 [ADR-0002](./adr/0002-dual-repository-data-access.md)）。

### 9.2 现实约束（必须写进文档，避免自欺）

- **存储与缓存被明文禁止（已核中文站一手条文）**：协议 3.5 条原文——「您只可使用在平台网站相应官方文档中所列明和开放的本服务的功能来对相关服务数据的结果进行展示，但是您**不得直接存储、缓存或技术手段抓取、使用本服务内部数据、图片等相关内容**」。→ 即**展示允许、存储禁止**。我们**永不落库或缓存真实接口返回的数据**；离线语料只放许可明确的开放数据集。
- **不得用于训练与数据集构建（同协议 3.4 条）**：「不得将本服务及相关内容用于模型或算法训练及相关数据集构建」。→ 由此推出本项目的关键结论：**回归评测不能建立在真实接口之上**。这与配额多少无关——结果不许留存，就构不成可复现的回归集。
- **配额（已核官方定价页）**：个人认证开发者的免费月配额为——基础搜索服务（关键字/周边/多边形/ID 搜索、输入提示）**5,000 次/月**，天气查询 5,000 次/月，基础 LBS 服务（路径规划、地理编码、距离测量等）**150,000 次/月**；超限可按 30 元/万次购买流量包。免费额度仅限「个人研究学习目的」。→ 配额压力小于预期，**约束来自条款而非额度**。
- **仅限自用（同协议 3.6 条）**：「**原则上仅限于您自己使用本服务**」；交由第三方实际使用需经同意并事先告知。→ 这是 §3「不公网部署」与 §4.3 砍单的直接依据。
- **住宿、门票、实时价格：个人开发者没有合规渠道**。抓取不是灰色地带——公开判例已确立「实质替代即不正当竞争」「绕过技术措施即不正当竞争」。→ 不抓，降级为区域选址建议。
- **票务**：官方明确否认向第三方开放接口。→ 只读、可失败、显著标注、绝不下单。

### 9.3 核实状态

**已核实（一手来源见 [合规核实报告](./research/2026-amap-compliance-verify.md)）**：中文站协议关于存储/缓存/抓取的禁令；不得用于训练与数据集构建；服务仅限自用；个人配额的准确数值；商业目的需技术服务许可。

## 10. 技术栈

语言 Python；编排使用编排外壳 + 规划图两层（见 [ADR-0003](./adr/0003-outer-state-machine-inner-graph.md)）；约束求解使用 CP-SAT 类求解器（见 [ADR-0001](./adr/0001-constraint-solver-in-the-loop.md)）；存储使用单一关系库承载会话状态、方案版本、画像与向量；模型走 OpenAI 兼容接口以便切换（开发期用免费模型压成本，演示与评测用低价高性能模型）；检索使用本地向量模型 + 重排模型以支持离线复现；可观测性使用托管观测服务。细节见 [architecture.md](./architecture.md)。

## 11. 路线图（阶段制）

每个阶段都必须产出**可演示**的东西，禁止最后一步才集成。完成标志是「可演示产出」，不是时间。

| 阶段 | 目标 | 可演示产出 | 状态 |
|---|---|---|---|
| **S1** | **图骨架**：共享状态、条件边、中断与澄清、真实槽位抽取 | 命令行里跑通「输入需求 → 追问缺失信息 → 从断点继续」 | ✅ 已完成 |
| **S2** | **数据访问层**：接口 + 离线实现 + 真实实现 | 「给定需求 → 取回候选池」并打印来源 | ✅ 已完成 |
| **S3** | **求解器与红线断言** | 一份通过全部红线断言的方案 | ⬜ 下一步 |
| **S4** | **意图路由 + 长途主线闭环** | 四类输入走四条不同的路，长途方案端到端产出 | ⬜ |
| **S5** | **短途主线 + 修改主线与方案版本** | 「改第二天的安排」并展示保留/重算清单 | ⬜ |
| **S6** | **编排外壳**：会话、幂等、超时重试、预算守卫、限流 | 同一请求重复提交返回同一方案版本 | ⬜ |
| **S7** | **评测闭环**：用例集、断言、消融、CI | 一张带口径的指标表 + 一次 badcase 迭代 | ⬜ |
| **S8** | **演示与包装**：Web 侧栏、录屏、README | 三分钟录屏 + 一键本地启动 | ⬜ |

> **S2 记账：可演示产出成立，但离线后端有一个前提，另有三处能力缺口。**
>
> - **前提：离线快照的城市名是罗马音**（`Harbin`，不是「哈尔滨」）。HOT 导出的行政区字段
>   只有 `adm2_name` 的罗马音形式，没有中文列。所以走离线后端时，需求里的城市名必须能被
>   检索命中——**中文城市名会得到空候选池**。这不是静默失败：候选池的输出会打印各类别取回
>   条数与「没有取到任何候选地点」，一眼能看出是名称对不上而不是城市里没有地点。
>   真实后端（高德）没有这个问题。
> - **离线天气恒不可用**：快照有一个 `source` 与一个 `license` 字段，把 ODbL 的地点与
>   CC-BY 的天气混进一张表会让逐条来源标记变成假话，所以抓取脚本不抓天气。
> - **离线侧断言不了 A3**：`opening_hours` 缺失约 98%（真实快照实测 1/132）。这不是
>   「数据差一点」，而是**这条断言在离线回归里没有依据**，必须记账而不是让它悄悄通过。
> - **离线侧没有 adcode**：HOT 有 `adm2_pcode`，但那是 OCHA/HDX 的编码体系，与高德 adcode
>   不是一回事，两者不混用。天气接口要 adcode，这在离线侧又堵死一条路。
>
> 已知缺口的完整清单在 [data/README.md](../data/README.md) 与
> [architecture.md §7.3](./architecture.md)。

### 与初版的差异（以及为什么）

初版按「周」排，把**图骨架**与**编排外壳**塞进同一个 W1。实际执行时顺序调整了：先做图骨架，外壳推迟。三处改动记在这里，避免日后对不上账。

**① 为什么外壳排到 S6。** 会话、幂等、限流都是为「真实使用」服务的，而澄清靠 `thread_id` 已经能工作——**在有 Web 界面之前，外壳没有服务对象**。这不是砍掉，是挪后。

**② 为什么意图路由排到 S4。** 路由要分出「长途 / 短途 / 修改 / 超范围」四条主线，而**主线本身还没实现时，路由没有可分的东西**。当前的条件边分的是「信息全不全」，那是**完整性判定**，不是意图路由——两者不是一回事（见 [architecture.md §2](./architecture.md) 对「外壳职责」与「图内节点」的划分）。

**③ 为什么改成阶段制。** 初版的「6 周 × 每周 10–15 小时」是一个预算刻度，执行中它失去了意义：真实进度由「一个机制是否被验证」决定，不由日历决定。保留时间刻度只会让人误判完成度——初版把 W1 报成「完成」而实际只完成一半，就是这么来的。

## 13. 对外讲述要点

**统一叙事结构**：`约束 → 选择 → 证据 → 边界 → 改进`。

**三分钟版**：
> 我把旅行规划重定义成一个约束满足问题。行业基准显示 SOTA 模型生成的行程达到人类水平的不到 10%，失败在可行性上——所以我没有让模型去保证可行，而是让确定性求解器保证，模型只负责理解需求和解释方案。代价是候选池必须小而准，这又受限于地图接口每天百次量级的检索配额和禁止落库的条款，于是我把数据访问做成双实现：离线数据集跑评测，真实接口跑演示。评测是一组确定性断言加 24 条回归用例，红线违反数恒为 0；另外三组消融用来回答「多一套 Agent、多一路检索到底有没有用」。

**必答问题与准备方向**：
1. 为什么用编排 + 图两层，而不是全塞进图？→ 可审计、可单测、权限与幂等属于确定性逻辑（[ADR-0003](./adr/0003-outer-state-machine-inner-graph.md)）。
2. 为什么硬约束交给求解器？→ 语言模型无法强制过滤约束；求解器还能把「不可行」变成一次高质量的澄清（[ADR-0001](./adr/0001-constraint-solver-in-the-loop.md)）。
3. 多 Agent 到底带来什么？→ 给消融数字；如果收益有限就直说。
4. 怎么防止模型编造地点？→ 候选池 + ID 命中断言（A1），不是 prompt 祈祷。
5. 数据合规怎么处理的？→ 引条款原文（3.5 展示允许存储禁止、3.4 禁止数据集构建、3.6 仅限自用）、双路径隔离、以及我们主动放弃的功能；并主动说明「约束来自条款而非额度」，不夸大困难。
6. 讲一个真实的失败样本。→ 见 §1 C5 的迭代链。
