# 硬约束交给约束求解器，语言模型不做可行性判定

行程的硬约束（预算、时间窗、营业时间、通勤、返程可达）是一组耦合的数学条件。语言模型擅长理解需求与表达方案，但不具备**强制过滤**约束的能力——它只能把约束当作文本倾向来匹配，因此必然存在不可控的违规率，且重生成次数不可预测（成本与延迟随之抖动）。我们决定：候选池由模型与工具产生，**硬约束下的组合与排序由 CP-SAT 类求解器求出**，模型只负责理解需求、提出候选归属与解释结果。

## 考虑过的方案

- **事后校验**：模型直接生成完整行程，校验器判定违规后回灌重生成。实现最快，但违规率永远不为零，且重生成次数不可控。
- **全确定性求解**：模型只做自然语言理解与解释。放弃这一档是因为它会抽掉本项目中检索增强、记忆与多环节编排的全部存在理由。
- **（选定）求解器在环**：模型产出候选，求解器决定可行性，不可行时返回最小冲突集。

## 影响

- 红线违反数从「测得低」变为**结构性为零**——无效方案在构造上无法生成。
- 求解器的失败（不可行）被转化为**一次高质量澄清**：把冲突的约束集合翻译成带选项的问题。这是本方案独有的产品收益。
- 代价：项目多一层建模工作，且模型的自由度被限制在候选池内。候选池因此必须小而准，这与地图接口的检索配额（每日百次量级）恰好同向。
- 若未来引入新的硬约束（例如新的同行人限制），只需扩展约束模型与断言，不需要重新调提示词。
