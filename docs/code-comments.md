# 代码注释规范

> 这不是代码风格规范（缩进、命名、行长不在这里）。它只回答一个问题：**什么该写进注释，什么不该。**
>
> 一句话立场：**本项目要求注释规范且丰富——但丰富不等于多。注释的敌人是复述，不是简略。**

---

## 一、注释是第五层文档

本项目已有四层文档，注释必须与它们分工，绝不能重复：

| 层 | 文件 | 回答什么问题 |
|---|---|---|
| 词汇 | [CONTEXT.md](../CONTEXT.md) | 这个词是什么意思 |
| 产品 | [prd.md](./prd.md) | 为什么做、不做什么 |
| 实现 | [architecture.md](./architecture.md) | 整体怎么搭 |
| 决策 | [adr/](./adr/) | 为什么偏偏这么做 |
| **注释** | **代码里** | **这一行为什么必须是这样** |

**推论：注释不复述上层文档，只补充「上层没说、但读代码的人一定会猜错」的东西。**

需要解释术语时给出指向，不要在代码里重新定义：

```python
# ✅ 好：指向词汇表
# 「保留项」的定义见 CONTEXT.md。这里的判断只处理已确认的停靠点。

# ❌ 坏：在代码里重新定义概念
# 保留项指的是用户在修改方案时明确要求不要变动的内容，包括……
```

后者的问题是**两处维护必然分叉**：词汇表改了，注释不会跟着改。

## 二、必须写的三类注释

### 1. 模块 docstring：说位置，尤其要说「不做的事」

```python
"""求解器：在硬约束下求出行程的时间与顺序安排。

位置：决策层，被规划图的 solve 节点调用（见 docs/architecture.md §4）。
可测试性：纯函数，无网络、无模型调用，因此可以进 CI 对历史方案批量回归。
不做的事：不生成候选、不改写候选、不判断软偏好——那是 draft 与 narrate 的职责。
"""
```

**「不做的事」是模板里最重要的那一行。** 它挡住的不是外部调用者，是三个月后的你自己——模块腐化几乎总是从「顺手在这里多干一点」开始的。

### 2. 行内注释：只写「为什么」，不写「什么」

判据只有一条：

> **如果这段代码看起来可以简化、但你偏偏没有简化，就必须注释。**

否则接手的人（大概率是你）会把它「优化」掉，然后让一个已经修好的 bug 复活。

三个必须注释的信号：

| 信号 | 例子 |
|---|---|
| **反直觉的边界算术** | 用 `>` 而不是 `>=`，因为轮次号已经被自增过 |
| **为绕开某个具体失败而写的防御** | 因为上游在超限时返回的是空数组而不是错误码 |
| **有更直观写法但代价更高** | 不用 `operator.add` 而按 id 去重合并，因为外层有循环 |

对照：

```python
# ✅ 好：解释了为什么不能写成看起来更简单的版本
def merge_candidates(old: list[dict], new: list[dict]) -> list[dict]:
    """按 id 合并候选池，重复的保留先到的那个。

    不能用 operator.add：图里有修复循环，取候选的节点会跑第二次、第三次，
    直接拼接会让重复 id 进入候选池，使红线断言 A1（按 id 命中）失去意义。
    """
    merged = {c["id"]: c for c in old}
    for c in new:
        merged.setdefault(c["id"], c)
    return list(merged.values())
```

```python
# ❌ 坏：复述函数名，零信息，且会随实现腐烂
def merge_candidates(old, new):
    # 合并候选
    ...
```

### 3. 契约注释：函数签名表达不了的东西

签名能表达类型，表达不了这四件事，必须写进 docstring：

| 类别 | 要写清什么 |
|---|---|
| **副作用** | 写了哪个存储、发了哪个外部请求、改了哪个全局状态 |
| **幂等性** | 能不能重复调用；重复调用的后果是累加、覆盖，还是会报错 |
| **单位与口径** | 秒还是毫秒；含税还是不含；预算是上限还是期望值 |
| **失败模式** | 什么情况下抛、抛什么、调用者应该重试还是降级 |

本项目的 `data/` 层尤其关键——**「不落库」是一条产品红线，必须写在每个实现的 docstring 里**，否则它会随着某次「顺手加个缓存」而失效。

## 三、注释密度按「猜错的概率」分档

不要所有文件一个密度。密度应该正比于**读代码的人猜错的概率**，不是正比于心情或行数。

| 模块 | 密度 | 为什么 |
|---|---|---|
| `graph/` | **高** | 状态语义（哪个字段挂 reducer、覆盖还是累加）与循环停止条件，是全项目最反直觉的地方 |
| `solver/` | **高** | 每一条约束都对应一条产品红线，必须能逐条追溯 |
| `verify/` | **高** | 每条断言都要注明它守护的是哪条红线编号 |
| `data/` | 中 | 接口契约 + 合规纪律 |
| `shell/` | 中 | 路由规则与幂等键的构造方式 |
| 纯数据结构字段 | 低 | 字段名自解释；只注释非显然的（如 `repair_count` 的上限来自哪里） |

「高」的含义不是每行都有注释，而是**每个反直觉的决定都有注释**。

## 四、术语必须用 CONTEXT.md 的词

这是本规范里**唯一可以机械检查**的一条，因此没有借口。

| 用 | 不用（`_Avoid_`） |
|---|---|
| 停靠点 | 景点、打卡点 |
| 方案 | 行程单、规划书 |
| 行程 | 路线、日程表 |
| 硬约束 | 限制、条件、要求 |
| 修改 | 重规划 |

`_Avoid_` 里的词一旦出现在注释里就是违规——**它意味着代码和词汇表已经分叉**，而分叉的语言会让后来者无法确定两个词指的是不是一个东西。

## 五、不许写的六类

| 不许 | 为什么 |
|---|---|
| **复述代码** | 零信息，且会随代码腐烂。`i += 1  # i 加一` |
| **复述上层文档** | 两处维护必然分叉。在代码里解释「什么是硬约束」 |
| **注释掉的代码** | git 记得住，注释记不住。`# old_impl(x, y)` |
| **裸 TODO** | 没人知道为什么、什么时候、谁来做 |
| **历史叙述** | 那是 `git log` 的活。`# 以前是这么写的` |
| **装饰性分隔线轰炸** | 视觉噪音。每五行一条 `# =====` |

**TODO 的正确写法**：带日期、带原因、带去处。

```python
# ✅ 好
# TODO(2026-11): 目前只解单日指派；跨日容量是 ADR-0001 里记的后续项。
# 不做的原因：6 周预算内优先保证单日可行性为 0 违反。

# ❌ 坏
# TODO: 优化这里
```

## 六、注释与代码必须同步改

**过期的注释比没有注释更糟——它主动误导。**

改行为的提交里如果没改紧邻的注释，就是漏了。自查动作：提交前看一遍 `git diff`，凡是「改了代码但旁边注释没动」的地方，逐个确认是注释仍然成立，还是自己忘了改。

注释也不是越多越好：**一处过期的复杂注释，比删掉它更有害。** 拿不准时，删注释比留错注释好。

---

## 七、可机械检查的清单

前四条可以写成脚本或钩子（[CONTRIBUTING.md](../CONTRIBUTING.md) 的第五节已有钩子机制，未来可挂在 pre-commit 上）：

1. 每个模块有 docstring，且包含「不做的事」
2. 每个公开函数有 docstring，且四类契约信息（副作用/幂等/单位/失败）至少覆盖适用的部分
3. 不出现 [CONTEXT.md](../CONTEXT.md) 中 `_Avoid_` 列出的同义词
4. 不出现不带原因与去处的 `TODO`
5. 不出现注释掉的代码块（人眼检查）
6. 密度分档符合第三节（人眼检查）

## 八、一个完整的正反对照

以「校验节点」为例。

```python
# ❌ 坏：三个问题——复述代码、没有红线编号、没写副作用
def verify(state):
    """校验方案。"""
    # 检查每个停靠点是否在候选池里
    pool_ids = {c["id"] for c in state["candidates"]}
    bad = [s for s in state["plan"]["stops"] if s["poi_id"] not in pool_ids]
    if bad:
        return {"failures": ["有停靠点不在候选池"]}
    return {"failures": []}
```

```python
# ✅ 好
def verify(state: TripState) -> dict:
    """执行红线断言，返回失败项列表。

    位置：规划图的 verify 节点（见 docs/architecture.md §5）。
    副作用：无。纯函数，不读存储、不发请求、不调模型。
    幂等性：是——可在 CI 中对历史方案批量重跑，这是评测闭环的前提。
    失败模式：不抛异常。方案结构缺失时返回失败项，由调用方决定修复还是降级。

    本函数守护的红线：R2（方案中每个停靠点必须来自候选池）。
    完整断言清单见 docs/prd.md §7.1。
    """
    # A1 零虚构地名：按 ID 命中候选池，而不是按名称比对。
    # 名称比对会让「同名不同店」漏过，也挡不住模型微调过的地名。
    pool_ids = {c["id"] for c in state["candidates"]}
    bad = [s for s in plan.get("stops", []) if s["poi_id"] not in pool_ids]
    ...
```

差别不在行数，在于：**好的那份让一个没读过 PRD 的人也知道这条判断为什么必须存在、以及它坏了会怎样。**

## 九、与本项目其他规范的关系

- 命名与术语：以 [CONTEXT.md](../CONTEXT.md) 为准（本文件第四节是它在代码里的落点）
- 提交信息：见 [CONTRIBUTING.md](../CONTRIBUTING.md) 第一节
- 文档边界：产品写 [prd.md](./prd.md)、实现写 [architecture.md](./architecture.md)、词汇只放 [CONTEXT.md](../CONTEXT.md)——**注释不要越界去补这些文件该写的内容，那是那些文件的问题，去改它们。**
