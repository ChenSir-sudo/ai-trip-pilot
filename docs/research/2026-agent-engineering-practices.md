# 生产级 Agent 项目的工程特征（调研）

> 调研日：2026-10-10。
> 方法：检索企业技术文章与框架官方文档，归纳生产级 Agent 项目的共性工程特征。
> 用途：为 [docs/prd.md](../prd.md) 与 [docs/adr/](../adr/) 的决策提供外部依据。
> 标注：✅ 已核实一手来源 ｜ ⚠️ 二次来源 ｜ ❓ 未确认。

---

## 0. 一句话结论

**能经受追问的 Agent 项目，与「跑得起来的 demo」之间的差别不在技术栈，而在两件事：能不能证明它有效，以及怎么防止它变差。**

---

## 1. 从最简方案起步，只在能证明收益时加复杂度

- **Anthropic《Building Effective Agents》**：从最简方案起步，只在能证明收益时才增加复杂度（[原文](https://www.anthropic.com/engineering/building-effective-agents)）。✅
- **企业实践**：Workflow 覆盖 90% 常态 + Agent 处理 10% 异常的「双轨制」（[腾讯云复盘](https://cloud.tencent.com.cn/developer/article/2672153)）。⚠️
- **编排形态的共识**：**外层状态机（确定、可审计、权限、恢复）+ 内层图编排（动态规划）** 混合（[阿里云](https://developer.aliyun.com/article/1754424)）。✅

**判断「该用 Agent 还是固定 Workflow」的四个维度**：路径是否已知、错误成本多高、是否需运行时动态判断、时延稳定性要求。

→ 本项目采纳「外层状态机 + 内层图」为 [ADR-0003](../adr/0003-outer-state-machine-inner-graph.md)。

---

## 2. 多 Agent 的收益必须被证明

**角色名称本身不构成架构价值**——多 Agent 相对单 Agent 的收益必须给消融实验：成功率、P95 延迟、成本、冲突率。

这是一条**归纳判断**（见 §8），但它对本项目意味着一个明确的可执行动作：**给多 Agent 加一条证伪条款**。

→ 本项目采纳为 [ADR-0004](../adr/0004-multi-agent-evidence-gated.md)：多 Agent 的保留是有条件的，消融通不过就降级为单 Agent。

---

## 3. 评测：分层与口径

**「准确率」必须分层说清指什么：**

| 层 | 指标 |
|---|---|
| 检索层 | Recall@K、MRR、nDCG |
| 生成层 | 忠实度、引用正确率 |
| 系统层 | 成功率、延迟、成本 |
| Agent 层 | 工具选对、参数 schema 对、无副作用、结果被正确使用 |

**「评测器本身对不对」的标准做法**：**红线段用确定性断言**，主观质量才交模型裁判并人工抽样校准；固定回归集与隐藏挑战集分离（[阿里云·质量闭环](https://developer.aliyun.com/article/1768633)）。✅

**badcase 的迭代链**：漏检 → Trace 定位 → 加断言 → 版本对比 → CI 阻断。

→ 本项目采纳为 [prd.md §7](../prd.md)。

---

## 4. 工程与成本

- **失败处理**：可重试性分类 + 指数退避 + 幂等键 + 先查状态再重试 + 熔断降级 + checkpoint。
- **成本拆桶**：输入、输出、检索、重排、工具调用、重试——分开记才能回答「钱花在哪」。
- **预算守卫**：说明它在哪一层，以及超限后是拒绝、缩上下文、换路由还是转人工。

## 5. 「能跑的 demo」与「可验证的系统」

| 维度 | 只能跑的 demo | 可验证的系统 |
|---|---|---|
| 问题范围 | 万能助手 | 窄场景 + 明确不做什么 |
| 失败证据 | 只有成功截图 | **一条真实的失败样本**：错在输入 / 检索 / 提示词 / 界面 |
| 评测 | 「准确率很高」 | 可复用的用例集 + 断言 + 报告 + **红线指标** |
| 迭代 | 无 | 改了什么 → 哪条变失败 → 怎么定位 → 有没有伤及他处 |
| 工程 | 只列框架名 | 鉴权、幂等、版本、超时、降级、审计、成本上限 |
| 表达 | 「基于 RAG 的问答系统」 | **业务对象在前** |

**被反复提到的可信信号**：评测集与指标（含基线口径）、可回放的 Trace、CI 阻断回归、README 结构（问题—架构—快速开始—评测结果—失败案例—限制）、真实用户量（没有就写「原型 / 离线测试」，不假装生产）。

**汇报纪律**：每个数字必须带样本量、口径、时间窗口、基线；**没测过就写「未测」，不补造百分比**；不把框架能力说成自研。

> 本节的表格与信号清单是**综合归纳（推断）**，不是单一来源的结论。它的价值在于可执行：每一条都能转成一个具体的验收标准。

## 6. 同类项目的通病

| # | 通病 | 证据 |
|---|---|---|
| ① | **模板化** | 公开仓库已有成熟的多 Agent 旅行规划项目（[multi-agent-travel-planner](https://github.com/bcefghj/multi-agent-travel-planner)）⚠️ |
| ② | **只调 API，不保证约束成立** | 一篇旅游 Agent 复盘自述：纯提示词方案上线三天即崩（给 3 岁孩子排冲浪、无视预算）⚠️ |
| ③ | **隐私** | 安全审计发现行程坐标、偏好、邮箱外传（[ClawHub 审计](https://docs.clawhub.ai/barneyjm/skills/travel-planner/security-audit)）⚠️ |

> **关于 ② 中那个「硬约束满足率 63.7%」的数字**：它出自单篇自述博客，n=1、自报、无口径。
> 因此**本项目不引用这个数字作论据**，只采纳它背后的机制论证——语言模型无法强制过滤约束。
> 所有指标一律由本项目自己测出，并带口径。这条纪律见 [prd.md §7.4](../prd.md)。

## 7. 出行场景的差异化方向

**把行程生成重定义为约束满足 / 组合优化：**

- 硬约束（预算、开放时间、通勤、同行人限制）交求解器保证，**报「红线违反数 = 0」而不是笼统的准确率**；
- 语言模型只做意图理解、候选生成与解释；
- 每条推荐可溯源（每个候选带来源标记）；
- 修改方案时讲清保留哪些已确认内容、幂等与版本如何避免重复副作用；
- 记忆分层，并说明写入前的重要性判断与冲突处理。

→ 对应本项目的 [ADR-0001](../adr/0001-constraint-solver-in-the-loop.md) 与 [prd.md §5](../prd.md) 红线。
